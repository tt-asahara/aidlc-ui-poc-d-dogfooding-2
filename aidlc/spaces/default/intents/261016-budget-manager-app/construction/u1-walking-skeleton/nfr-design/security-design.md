## 外部への通信を止める（NFR3）

### Content-Security-Policy（Q1、レビュー R-01）

ビルドしたページ（`index.html`）の見出し部分に、meta 要素で次の指定を入れます。

```text
default-src 'none';
script-src 'self';
style-src 'self';
img-src 'self';
font-src 'self';
connect-src 'none';
form-action 'none';
base-uri 'none';
object-src 'none';
frame-src 'none'
```

| 指定 | 意味 | 対応する要件 |
|------|------|-------------|
| default-src 'none' | 指定のないものは何も読み込ませない | NFR3.1 |
| script-src 'self' | スクリプトは自分のファイルだけ。ページの中に直接書いたスクリプトと、文字から命令を作る仕組み（eval）は動かない | NFR3.1、NFR4.1 |
| style-src 'self' | 見た目の指定は自分の CSS ファイルだけ。style 属性は使わない（Q1） | NFR3.1 |
| img-src、font-src 'self' | 画像と書体は自分のファイルだけ。外部の書体は読み込まない | NFR3.1、NFR3.2 |
| connect-src 'none' | 通信を一切させない | NFR3.1、NFR3.3 |
| form-action、base-uri、object-src、frame-src | フォームの送信先、基準の URL、プラグイン、埋め込みを禁止する | NFR3.1 |

入れ方:

- Vite のビルドのときだけ、`index.html` に上の meta 要素を足す設定にします。開発中の起動では、変更をすぐ画面に反映する仕組みが手元の通信を使うため、入れません。
- Vite は既定で、小さな画像や書体を data: の URL としてページに埋め込みます（build.assetsInlineLimit）。上の指定は data: を許さないため、ビルドの設定で assetsInlineLimit を 0 にし、すべてを自分のファイルとして出力します。data: の読み込みがないことは NFR3.2 の検査で確かめます。
- meta 要素では効かない指定（埋め込み元の制限 frame-ancestors、違反の報告先）は使いません。ページは手元でだけ使い、ほかのサイトに埋め込まれる場面がないためです。
- CSV のダウンロードは、手元で作ったデータ（Blob）の一時的な URL を使い、通信は発生しません。Chromium・Firefox・WebKit のブラウザ操作のテストで、この指定の下でもダウンロードできることを確かめます。

### 確かめ方

| ID | 確かめ方 |
|----|----------|
| NFR3.1 | 単体テストで、ビルドの設定が meta 要素を足すことを確かめる。Playwright で、ページに外部の画像を差し込もうとすると、ブラウザが止めることを確かめる |
| NFR3.2 | ビルドのあとのテストで、ビルドの出力（`app/dist/`）の「読み込み先」だけを調べ、外部（`http://`・`https://`・`//` で始まるもの）と data: がないことを確かめる。対象は次の3つ。<br>・`index.html` の src と href<br>・CSS の url() と @import<br>・JS の動的な読み込み（import()）の行き先<br>JS の中の文字列全体は調べない。React DOM の出力には、仕様上の名前（`http://www.w3.org/2000/svg` など）やエラーの案内の URL が文字列として含まれるが、どれも読み込みには使われないためである。実際の読み込みと通信が外部へ出ないことは、CSP（NFR3.1）と通信の記録（NFR3.3）で確かめる |
| NFR3.3 | Playwright で、登録 → 集計 → CSV 出力の間のすべての通信を記録し、ページの配信元と違う先が 0 件であることを確かめる |
| NFR3.4 | テストのデータは、決まった規則で作る架空の明細だけにする。実在の名前を含めない |

## 文字と保存データの扱い（NFR4）

| ID | 設計 |
|----|------|
| NFR4.1 | 利用者の文字は、React の通常の表示（文字として差し込まれる）だけで出す。ESLint で、HTML として差し込む書き方（`react/no-danger`）と、文字から命令を作る書き方（`no-eval`、`no-new-func`）を禁止する |
| NFR4.2 | CSV の値は、カンマかダブルクォートを含むときだけダブルクォートで囲み、中の " を "" にする（BR3.3）。数式対策は U4 で足す。U4 までの CSV は、表計算ソフトで開く前提の控えとしては使わない（開発中の試作） |
| NFR4.3 | DataStore.load は、保存領域の文字を JSON として読む処理を失敗に備えて囲む（try）。読めない、または版（schemaVersion）が 1 でないときは unreadable を返す（BR4.2）。読めた保存データの項目の検査（型・範囲）は U5 で足す |
| NFR4.4 | アプリが動くときの部品は React と React DOM だけにする。部品を足したときは npm audit を実行し、critical・high を残さない。残す場合は理由を記録して依頼者に知らせる |
| NFR4.5 | 秘密情報を扱わない。環境変数も使わない |

## 信頼性の設計（NFR5、Q4）

### 保存の手順（DataStore.commit）

1. 状態が unreadable なら、何もせず STORE_UNREADABLE を返す。
2. 新しい保存データを手元で組み立てる（今の保存データ + 変更、通し番号 + 1、保存した時刻）。この時点では、手元の写しは変えない。
3. 保存領域の文字を読み直し、通し番号を取り出す。結果ごとに分かれる。
   - **何もない**: 0 とする（BR4.1）。
   - **保存領域へのアクセス自体が失敗する（例外が起きる）**: 何もないときと同じに扱い、手順 5 へ進む。手順 5 の書き込みも失敗するので、STORAGE_WRITE になる。
   - **保存されている文字が JSON として読めない、または版が 1 でない**: 保存せず STORE_UNREADABLE を返し、状態を unreadable にする。

   「アクセスできない」と「保存データが壊れている」を分けることで、起動時の扱い（下の「起動時に保存領域が使えないとき」）と一致させる。
4. 通し番号が期待する値と違えば、保存せず STALE_REVISION を返す。読み直した内容を手元の写しにし、`externalChange` を知らせる（BR4.4）。
5. 保存領域に新しい保存データ全体を1回で書く。書き込みの失敗（容量不足 QuotaExceededError、使えない SecurityError など）は、すべて STORAGE_WRITE として返し、手元の写しは変えない（NFR5.2）。
6. 成功したら、手元の写しを新しい保存データにして `committed` を知らせる（BR4.5）。

| ID | 設計 |
|----|------|
| NFR5.1 | 手順 5 で、保存データ全体を1つの値として1回で書く。localStorage の1回の書き込みは、全部書かれるか何も書かれないかのどちらかになる |
| NFR5.2 | 手順 2 と 5 で、成功するまで手元の写しを変えない。失敗したら画面は前の内容のまま、入力は残す（W4）。自動ではやり直さない（Q4） |
| NFR5.3 | 起動時と手順 3 で読めないときは、保存領域に書かない。unreadable の状態では、どの保存の操作も手順 1 で止まる（BR4.2、BR4.6） |
| NFR5.4 | 手順 3 と 4 の通し番号の照合。読み直しと書き込みの間に別のタブが書く隙間は残る。U5 で、排他の仕組みで閉じるか、残るリスクとして記録する（契約レビュー R-03） |

### 起動時に保存領域が使えないとき

ブラウザの設定などで保存領域そのものが使えないときの、起動時の知らせ方は U5 で決めます（約束ごとの未解決の点）。U1 では、次のように扱います。

- 起動時の読み込みで保存領域へのアクセス自体が失敗したら、「保存データなし」と同じに扱います。
- 登録のときは、手順 3 のアクセス失敗の扱いにより、手順 5 で STORAGE_WRITE の表示（BR4.3）になります。
- STORE_UNREADABLE（BR4.2・BR4.6）になるのは、保存されている文字が壊れているときだけです。

### 予想外の失敗（Q3）

| 設計 | 内容 |
|------|------|
| 受け止める場所 | 「1 登録」「2 確認」「3 書き出し」のそれぞれを、React のエラーの受け止め（Error Boundary）で囲む。1つの区切りで失敗しても、ほかの区切りは使える。さらに、AppShell 全体を最も外側の Error Boundary で囲み、起動時の読み込みや組み立ての失敗でも画面が真っ白にならないようにする |
| 受け止められない箇所 | Error Boundary は表示中の失敗だけを受け止め、ボタンを押したときの処理（登録、CSV 保存）と非同期の処理の失敗は受け止めない。そのため、これらの処理は予想外の例外を try/catch で捕まえ、その区切りの状態に失敗を載せて、次の表示で Error Boundary に渡す |
| 表示 | 「問題が起きました。ページを再読み込みしてください。保存済みのデータは消えていません」を role=alert で出す |
| 記録 | 詳しい内容は、ブラウザのコンソール（console.error）にだけ出す。外部には送らない（NFR3）。利用者の入力した文字は記録に含めない |
| 予想できる失敗 | 入力の誤りと保存の失敗は、例外ではなく結果の値（C1）で返し、受け止めの仕組みには届かない |

## 監視について

外部への送信をしないため、監視の仕組みや記録の集約は置きません。確かめたい性質（時間、外部通信 0 件、アクセシビリティ）は、テストで確かめます（`performance-design.md`）。
