## 性能の設計（NFR1）

### データの持ち方

| 設計 | 内容 | 対応する要件 |
|------|------|-------------|
| 読み込みは起動時の1回 | DataStore は起動時に保存領域から保存データを1回読み、画面で使う写しを手元（メモリ）に持つ。画面の表示のたびに保存領域を読み直さない | NFR1.1、NFR1.2、NFR1.3 |
| 書き込みは全体を1回 | 登録のたびに保存データ全体を文字列にして1回で書く（NFR5.1）。3,000 件でおよそ 300〜400 KB で、localStorage の容量（一般に 5 MB 前後）に収まる | NFR1.1 |
| 月ごとの取り出し | Ledger.listByMonth は、明細を1回たどって表示中の月の分だけを取り出す。3,000 件では索引を作らなくても十分速い。索引は、計測で足りないと分かったときにだけ足す | NFR1.2、NFR1.5 |
| 集計の再計算 | 表示中の月と保存データの通し番号が変わったときだけ、MonthlySummary.summarize を計算し直す（React の再計算を抑える仕組み（メモ化）を使う） | NFR1.1、NFR1.2、NFR1.5 |
| CSV の組み立て | 行の文字列を配列に集めて最後に1回つなぎ、UTF-8 のバイト列に変える。BOM を先頭に付ける | NFR1.4 |
| 金額の計算 | 円の整数だけを使う。最大の合計（2,999,999,700）は、JavaScript の数で誤差なく扱える範囲（約 9 × 10^15 まで）に収まる | NFR1.6 |

### 時間の内訳（1 秒の目標に対する目安）

| 処理 | 目安 | 対応する要件 |
|------|------|-------------|
| 入力の判定と明細の組み立て | 10 ミリ秒以内 | NFR1.1 |
| 保存（文字列にして書き込む） | 200 ミリ秒以内 | NFR1.1 |
| 集計の計算 | 100 ミリ秒以内 | NFR1.5 |
| 画面の再表示 | 300 ミリ秒以内 | NFR1.1、NFR1.2 |
| 起動時の読み込みと最初の表示 | 1 秒以内 | NFR1.3 |

合計で 1 秒に対して余裕を残します。内訳の目安は、単体テストで集計の計算（NFR1.5）と CSV の組み立て（NFR1.4）を測って確かめます。

### 計測の方法（Q2、レビュー R-02）

- 時間の判定は Chromium だけで行います。Firefox と WebKit では、同じ操作が完了することだけを確かめます（NFR6.1）。
- Playwright のテストで、3,000 件・1か月 100 件の保存データ（架空のもの）を、ページを開く前に保存領域へ入れておきます。
- 操作から表示が変わるまでの時間を3回測り、中央値で判定します。
- テストのデータは、決まった規則で作る架空の明細です（実在の名前を使わない。NFR3.4）。

## 利用環境の設計（NFR6）

| ID | 設計 |
|----|------|
| NFR6.1 | Playwright の設定に、Chromium・Firefox・WebKit の3つの実行先を置く。同じブラウザ操作のテストを3つすべてで動かす |
| NFR6.2 | CSS で、幅 1024px 以上は2列、768〜1023px は1列に切り替える（画面幅による切り替え）。Playwright で 1280px と 800px の2つの幅で確かめる |
| NFR6.3 | 文字の大きさと余白は、拡大に合わせて伸びる単位（rem）で指定する。Playwright で 200% 相当の表示（幅 640px・拡大率 2）で登録を1回確かめる |

## 使いやすさとアクセシビリティの設計（NFR2、NFR8）

| ID | 設計 |
|----|------|
| NFR2.1 | `frontend-components.md` のアクセシビリティの項目を、部品ごとに実装する。Testing Library のテストでは、役割と名前で部品を探す書き方（getByRole、getByLabelText）を使い、名前のない部品があればテストが失敗するようにする |
| NFR2.2 | Playwright と axe で、U1 の5つの状態（初期・登録成功・入力の誤り・保存失敗・保存データが読めない）を検査する。critical と serious の違反が 0 件であることを確かめる |
| NFR2.3 | Playwright で、Tab・Shift+Tab・矢印キー・Enter だけを使い、登録 → 月の切り替え → CSV 出力を行うテストを置く |
| NFR8.1 | 画面の見出し「1 登録」「2 確認」「3 書き出し」を順に置き、Playwright で見出しの順番を確かめる |

## 保守性とテストの設計（NFR7）

| ID | 設計 |
|----|------|
| NFR7.1 | TypeScript の設定で strict を有効にする。型の検査をテストとは別のコマンドで実行する |
| NFR7.2 | Vitest のカバレッジ計測（v8）で、`app/src` の行カバレッジ 80% を下限として設定する。下回ればコマンドが失敗する。ブラウザで動かす起動のファイル（`main.tsx`）など、単体テストの対象にならないものだけを計測から外し、その理由を設定に書く |
| NFR7.3 | Playwright のテストは、ビルドしたページを手元の配信の仕組み（Vite の preview）で開いて動かす。そのページには Content-Security-Policy が入っている（`security-design.md`）。preview は `127.0.0.1` の固定のポートで、strictPort を有効にする。テスト用のポートは依頼者が使うポートと分ける（`logical-components.md`） |
| NFR7.4 | Prettier と ESLint を npm のコマンドにし、指摘があれば失敗するようにする |
| NFR7.5 | 型の検査、整形、リンター、単体テスト、ビルド、ブラウザ操作のテストを、1つの npm のコマンドで順に実行できるようにする。確認コマンドの候補として、B1 の最初の確認のときに提案する |
