# チームの開発プラクティス

> 依頼者との確認（`practices-discovery-questions.md` の Q1〜Q8、要約確認「Looks correct」）を反映した確定版です。各項目の出典と判断の経緯は `evidence.md` にまとめています。

## Way of Working

私たちはトランクベース開発を土台とし、最終的な統合先は `main` とする。ただし `main` を直接変更することはしない。日々の作業はリモート `origin`（GitHub）上の作業ブランチ `feat/budget-manager-app` で行い、`main` への取り込みは最後に依頼者の明示的な承認を得てから行う。

- **作業開始前の確認**: 作業を始める前に、作業ブランチとリモートを確認する。
- **コミットとプッシュの時点**: AI-DLC の各ステージが承認されたとき、各 Unit の実装とテストが完了したとき、各バグ修正のときに、内容がわかるメッセージでコミットし、作業ブランチへプッシュする。
- **チェックポイントでの報告**: 各チェックポイントで、コミット SHA、プッシュ結果、未完了の項目を報告する。
- **並行作業のブランチ**: 並行して作業するときは、担当ごとに別のブランチと worktree を使う。担当ブランチ／worktree は `feat/budget-manager-app` から作成し、`feat/budget-manager-app` へ戻す。統合したあとはテストを再実行する。
- **`main` への取り込み**: `feat/budget-manager-app` から `main` への取り込みは、作業の最後に一度、依頼者の明示的な承認を得てから行う。取り込む前に、GitHub Actions で Prettier と ESLint が成功していることを確認する（`## Code Style` を参照）。
- **マージ方式**: 担当ブランチを統合するときは squash マージを使い、1 担当（Bolt）を 1 コミットにまとめる（org.md の既定に従う）。
- **途中状態の退避**: 未完成の内容を退避のためにコミットするときは、WIP であることを明示する。
- **禁止事項**: 強制プッシュはしない。依頼者の明示的な指示なしにマージはしない。秘密情報、個人データ、`node_modules` などはコミットしない。

## Walking Skeleton

最初に、全体を端から端まで通す最小の版（walking skeleton）を作る。

- 最初の Unit は「収支を 1 件登録 → 月次集計に反映 → CSV に出力」が最小限つながる版とする。機能は最小限でよいが、ブラウザ上で最初から最後まで動くこと。
- この Unit は、Code Generation を含む該当ステージをすべて通してから、ほかの Unit に進む。
- 動作確認には、依頼者が承認した Construction の検証コマンドを使い、実際に最初から最後まで動くことを示す。
- 依頼者がこの版を確認・承認してから、残りの機能を作る。

## Testing Posture

テストは各 Bolt の成果物の一部として扱う。

- **Methodology**: test-after
- **Methodology evidence**: 依頼者が Q1 で「実装してからテストを書く（テスト可能な部分ごとに、実装 → テストの順）」を選んだ。org.md の既定とも一致する。
- **Ordering**: テスト可能な層ごとに、まずその層を実装し、そのあとでその層のテストを書いて実行し、通ってから次の層に進む。
- **カバレッジの下限**: 行カバレッジ 80% 以上を保つ。下限を下げてステップを通すことはしない。
- **テストツール**: 単体テストに Vitest、ブラウザ操作のテストに Playwright を使う。
- **統合後の再実行**: 並行作業を `feat/budget-manager-app` へ統合したあとは、テストを再実行して結果を確認する。
- **既存テストの維持**: 既存のテストが通る状態を保つ。

## Deployment

当面は配置先の環境を持たず、依頼者のパソコンでのみ動かす。公開はしない。

- アプリは依頼者のパソコンのブラウザで動かし、データもそのブラウザ内に保持する。外部への送信はしない。
- org.md の「マージ時にステージング環境へ配置し、本番配置は手動承認とする」は、配置先の環境を用意した時点から適用する。それまでは適用しない。
- 公開先（静的ホスティングなど）を用意することになった場合は、その時点で配置方針を見直す。

## Code Style

言語は TypeScript とする。整形ツールは Prettier、リンターは ESLint を使い、設定はリポジトリ直下の設定ファイル（`.prettierrc`、ESLint の設定ファイルなど）で定める。

- **普段の実行**: Prettier と ESLint は、普段は依頼者のパソコン（ローカル）で実行する。
- **`main` へ取り込む前の実行**: `main` へ取り込む前には、GitHub Actions でも Prettier と ESLint を自動実行し、失敗した場合は取り込まない。GitHub Actions の設定は後の段階で用意する。
- **命名規則**: 言語の慣習に従う（TypeScript では camelCase）。プロジェクト独自の命名規則は設けない。
- 書式の指摘は、まずリポジトリの Prettier・ESLint の設定で扱い、設定で扱えない点だけを別途指摘する。
