# 機能設計（U5 保存の異常・別タブ対応・サンプル）— 質問

U5（`aidlc/spaces/default/intents/261016-budget-manager-app/inception/units-generation/unit-of-work.md`）は、U1 で作った保存の部品（DataStore）を仕上げます。受け持つストーリーは次の3つです。

- US7.1 サンプルデータで試し始める
- US7.3 保存できないときに気づく
- US7.4 2つのタブで食い違わない

U2〜U4 は、ここで固めた保存の結果と状態の上に作ります。

約束ごと（`inception/contract-design/contract-summary.md` の C2・C6・C9）、ストーリーの受け入れ条件、詳細モックアップ（全体のお知らせ枠）で、多くのことは決まっています。ここでは、契約レビューで U5 に持ち越した点と、まだ決まっていない点を確認します。どの質問も A がおすすめです。

すでに決まっていて、質問しないこと:

- **壊れた保存データ（AC7.3.3、AC7.3.4）:** 全体のお知らせ枠に「保存データを読み込めませんでした。データは消していません。」と止めている操作の説明を出し（role="alert"）、消さずに保存を止める。
- **別のタブの変更（AC7.4.1）:** 最新を読み込み、全体のお知らせ枠に「別のタブで変更がありました。最新の内容を読み込みました」を出す（role="status"）。
- **サンプル（C9）:** 明細と予算を1回の保存で入れ、保存データがまったくないときだけ入れる。
- **読み込み時の検査:** 保存データの項目を約束ごと C2 の形（型・範囲）と照らし、1つでも合わなければ「読めない」として扱う（U1 の最小限の判定を強化する）。

## Q1. 2つのタブがほぼ同時に保存したときの隙間は、どうしますか？

契約レビュー R-03 で指摘された点です。U1 の保存は、保存直前に通し番号を読み直して照合します。それでも、読み直しと書き込みの間（1 ミリ秒未満）に別のタブが書くと、後から書いた方が先の変更を上書きする隙間が残ります。

A. 残るリスクとして記録し、仕組みは足さない。1人が手で操作する使い方では、2つのタブで1 ミリ秒以内に保存が重なることは、現実には起きない。別のタブの変更の検知と、通し番号の照合で、ほとんどの場合は防げる（おすすめ。保存の呼び出しの形を変えずに済む）
B. ブラウザの排他の仕組み（Web Locks API）で保存を囲み、隙間をなくす。代わりに保存が非同期になるため、U1 の保存の呼び出し（Ledger.add と登録の画面）と約束ごと C2 の形を変える
C. 特に希望はない（おすすめでよい）
