## ADR-001: 明細と予算をまとめた1つのデータとして保存する

### Status
Accepted（依頼者がドメイン設計 Q1 で選択）

### Context
データはブラウザ内にだけ保持します（要件 FR9.1）。CSV の取り込みは全部追加されるか何も追加されないかにする必要があります（FR7.9、AC6.1.6）。壊れた保存データを見つけたら、データを消さずに保存系の操作を止めます（AC7.3.3、AC7.3.4）。別のタブでの変更は知らせて読み直します（US7.4）。データ量は全体で約 3,000 件までです（要件 Q8）。

### Decision
明細と予算を1つのまとまり（StoreSnapshot）として、DataStore という1つの部品がまとめて読み書きします。保存のたびに全体を書き、版（schemaVersion）と通し番号（revision）を付けます。

### Consequences
- 良い点: 取り込みの全部か無か、壊れたデータの検出、別タブの検知を1か所で扱える。明細と予算の整合が崩れない。
- 悪い点: 1件の登録でも全体を書き直す。約 3,000 件なら問題ない大きさと見込むが、性能は NFR 要件の段階で確かめる。
- セキュリティ: 外部へは送らない。保存データには架空データしか入らない（project.md の Mandated）。他のサイトからは読めないブラウザの保存領域を使う。

### Alternatives Rejected
- 明細と予算を別々に保存する（Q1 の B）: 2つの保存の間で失敗すると整合が崩れ、壊れたデータの扱いも2か所になるため採らない。
- 明細1件ごとに別々に保存する: 取り込みの全部か無かを守るのが難しく、件数が増えると読み込みも遅くなるため採らない。

## ADR-002: 月次集計を、読むだけの独立した部品にする

### Status
Accepted（依頼者がドメイン設計 Q2 で選択）

### Context
月次集計は収入・支出・差額と、支出カテゴリ別の予算・実績・残額・超過を出します（FR4、US3.1、US3.2）。カテゴリ別実績の合計が支出合計と一致すること、円の整数で誤差なく計算することが求められています（AC3.1.5、AC3.1.6）。

### Decision
MonthlySummary を独立させ、Ledger と Budget を読むだけにします。データの書き換えは行いません。

### Consequences
- 良い点: 計算を単独でテストでき、行カバレッジ 80% の目標（team-practices.md）を満たしやすい。明細と予算の部品が互いを知らずに済む。
- 悪い点: 部品の数が1つ増える。
- セキュリティ: 書き換えをしないため、集計の誤りでデータが壊れることはない。

### Alternatives Rejected
- Ledger の中で計算する（Q2 の B）: Ledger が予算を知る必要が生じ、明細の規則と集計の計算が同じ部品で変わることになるため採らない。

## ADR-003: CSV の出力・取り込みを独立した部品にする

### Status
Accepted（依頼者がドメイン設計 Q3 で選択）

### Context
CSV の形式（UTF-8 BOM 付き、日本語見出し）、数式対策、厳格な検証、重複の確認、取り込み結果の報告が決まっています（FR6、FR7、ストーリーの「要件との差分」、詳細モックアップ Q2・Q3）。CSV の取り込みは外から入るデータで、内容を信用できません。

### Decision
CsvExchange を独立させ、形式の変換・検証・重複の数え上げを集めます。明細の追加は Ledger の一括追加に頼み、Ledger は同じ規則でもう一度確かめます。

### Consequences
- 良い点: 形式や検証の変更が明細の規則に混ざらない。不正な入力の検証を入口で行える。
- 悪い点: 明細の規則（金額・日付・メモ）を CsvExchange と Ledger の両方で確かめることになる。規則そのものは Ledger の判定を使い、二重に定義しない。
- セキュリティ: 取り込みファイルは信用しない入力として扱い、大きさと行数に上限を設け、値は常に文字として扱う（要件 FR7.10、NFR4）。数式として実行されない対策を出力時に入れる（AC5.2.1）。

### Alternatives Rejected
- Ledger の中に入れる（Q3 の B）: 形式の変更が明細の規則と同じ部品で起き、テストの範囲も広がるため採らない。

## ADR-004: 画面は詳細モックアップの区切りごとに部品にし、計算と保存をさせない

### Status
Accepted（依頼者がドメイン設計 Q4 で選択）

### Context
画面は1画面の縦並びで、「1 登録」「2 確認」「3 書き出し」と全体のお知らせ枠からなります（詳細モックアップ `mockups.md`）。画面の振る舞いは Playwright で、計算は Vitest でテストします（team-practices.md）。

### Decision
EntryFormView、ReviewView、ExportView、NoticeBannerView を画面の部品とし、AppShell が配置します。画面の部品は計算や保存をせず、Ledger・Budget・MonthlySummary・CsvExchange に頼みます。

### Consequences
- 良い点: 画面の変更が計算や保存に及ばない。業務の規則を画面なしでテストできる。
- 悪い点: 表示中の月を AppShell から各画面に渡す必要がある。
- セキュリティ: 利用者が入力した文字は画面で常に文字として表示する（NFR4）。

### Alternatives Rejected
- 画面全体を1つの部品にする（Q4 の B）: 一部の変更が全体に及び、テストもしにくいため採らない。

## ADR-005: カテゴリの一覧を固定の部品として1か所に置く

### Status
Accepted（要件とストーリーから導いた判断）

### Context
カテゴリは収入3・支出8の固定で、利用者は編集できません（FR3、範囲定義書）。登録、予算、集計、CSV の取り込みの4か所が同じ一覧を使います。

### Decision
CategoryCatalog がカテゴリの一覧と、存在・区分との一致の判定を受け持ちます。一覧はプログラムに書き込み、保存データには含めません。

### Consequences
- 良い点: 4か所で一覧が食い違わない。保存データが壊れてもカテゴリは失われない。
- 悪い点: カテゴリを変えるにはプログラムの変更が必要（範囲外のため許容）。
- セキュリティ: 影響なし。

### Alternatives Rejected
- 各部品がそれぞれ一覧を持つ: 食い違いのおそれがあるため採らない。
- カテゴリを保存データに含める: 編集しないのに保存する理由がなく、壊れたときの影響が広がるため採らない。

## ADR-006: 初回のサンプル投入を独立した部品にし、データがまったくないときだけ動かす

### Status
Accepted（要件とストーリーから導いた判断）

### Context
初めて開いたときだけ直近3か月分の架空データを入れます（FR8、US7.1）。壊れた保存データを見つけたときは、サンプルを入れ直してはいけません（AC7.3.3）。

### Decision
SampleDataSeeder を独立させ、DataStore が「データなし」と報告したときだけ動かします。「壊れている」ときは動かしません。サンプルの明細と予算は Ledger と Budget の通常の追加・設定を通して入れます。

### Consequences
- 良い点: 壊れたデータをサンプルで上書きする事故を防げる。サンプルも通常の規則を通るため、規則違反のデータが入らない。
- 悪い点: 起動の順序（読み込み → 判定 → 投入）を AppShell が管理する必要がある。
- セキュリティ: サンプルは架空データのみで、実在の名前を含めない（AC7.1.4）。

### Alternatives Rejected
- DataStore の中でサンプルを入れる: 保存の部品が業務のデータの中身を知ることになるため採らない。
- 保存データが読めないときもサンプルで始め直す: 依頼者の決定（ユーザーストーリー Q5）に反するため採らない。
